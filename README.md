# AmneziaKeyService

Сервис выдачи VPN-ключей AmneziaVPN (`vpn://`) и подписок для приложения Happ, с Telegram-ботом
и веб-панелью администратора. Панель разворачивает VPN-узлы по SSH (AmneziaWG, WireGuard, VLESS Reality
и собственный Xray для подписок), выдаёт и отзывает ключи, ведёт учёт трафика, сроков и квот.

## Требования

- [.NET SDK](https://dotnet.microsoft.com/download/dotnet/10.0) версии из `global.json` (сейчас 10.0.201, `rollForward` отключён, prerelease не допускается);
- MongoDB 6+ (индексы используют `$in` в `partialFilterExpression`);
- Node 22+ для панели (`web/admin`); без него панель собирается через Docker (команда — в `CLAUDE.md`);
- Docker и Docker Compose для запуска всего стека (`docker compose up -d --build`);
- VPN-узел — VPS с Linux, доступный по SSH, с пользователем, у которого есть `sudo` без пароля. Docker на узле
  панель ставит сама. Узел `xcore` для подписок Happ предъявляет больше требований — см.
  [«Подписки Happ»](#подписки-happ).

## Быстрый старт

### 1. Создайте владельца и добавьте сервер через API

Сначала запустите worker: только он применяет миграции. Затем создайте
владельца из `ADMIN__USERNAME`/`ADMIN__PASSWORD` и добавьте сервер через
`POST /api/servers` или мастер панели. Этот путь записывает современный
`server_config` и шифрует SSH-пароль либо приватный ключ до сохранения в MongoDB.
Не создавайте документ узла напрямую через `mongosh`: плоская legacy-схема
больше не поддерживается.

### 2. Настройте appsettings.json

```json
{
  "MongoDb": {
    "ConnectionString": "mongodb://localhost:27017"
  },
  "Jwt": {
    "Secret": "минимум-32-символа-случайная-строка"
  }
}
```

Используйте `appsettings.Development.json` или переменные среды для секретов:
```bash
export Jwt__Secret="your-random-secret-here"
```

Без `Jwt__Secret` (не короче 32 байт) и `SECURITY__DATAPROTECTIONKEY` (ровно 32 байта в base64, им шифруются
SSH-доступы к узлам) сервис не стартует; владельца панели worker создаёт из `ADMIN__USERNAME` и `ADMIN__PASSWORD`.
Остальные переменные, в том числе настройки подписок и `xcore`, перечислены в `CLAUDE.md`.

### 3. Запустите сервис

```bash
cd src/AmneziaKeyService.Api
dotnet run
```

Swagger UI (только в Development): http://localhost:5116/swagger

## API

### Подключение уже настроенного VPN-сервера

В меню **Серверы → Подключить существующий** укажите адрес, SSH-порт и
пароль либо приватный ключ. Нажмите **«Найти установленные протоколы»**,
проверьте найденные порты, подсети и число существующих подключений, затем
выберите протоколы и нажмите **«Подключить выбранные»**.

Поддерживаются стандартные работающие контейнеры `amnezia-wireguard`,
`amnezia-awg`, `amnezia-awg2`, `amnezia-awg3`. AWG3 определяется также по
`HeaderProtectionKey` в конфигурации `amnezia-awg2`. Xray, `xcore` и контейнеры с
произвольными именами в этом режиме пока не импортируются.

Поиск и импорт выполняют только чтение по SSH: не устанавливают пакеты,
не меняют firewall, не перезапускают контейнеры и не переписывают конфиги.
Перед импортом конфигурация перечитывается; при изменениях нужно повторить
поиск. Остановленный контейнер, недоступные ключевые файлы, несовпадение
ключей/портов или клиентов в конфиге и работающем интерфейсе блокируют
подключение соответствующего протокола. Поддерживается один IPv4-адрес
интерфейса с маской /8–/30, первый адрес подсети (например, `10.8.1.1/24`),
и один публичный UDP-порт либо host networking. Адрес узла должен быть
доступен и по SSH из панели, и для VPN-клиентов.

Существующие подключения продолжают работать, но их владельцы, сроки,
квоты и история из потерянной базы не восстанавливаются. Они учитываются
как подключения без выданного панелью ключа. Занятые адреса берутся из
конфига при каждой новой выдаче. Перед подключением сохраните отдельную
копию конфигураций узла; не управляйте им одновременно из нескольких панелей.
Для проверки повторного добавления используйте одинаковый адрес и SSH-порт,
а не разные DNS-имена одного узла.

API (владелец/администратор): `POST /api/servers/discover` принимает SSH-доступ
и возвращает безопасный список протоколов с `revision`; `POST /api/servers/import`
принимает тот же доступ, метаданные, `revision` и выбранные имена `containers`.
Параметры протоколов и секреты перечитываются сервером, а не принимаются от
браузера. SSH-секреты шифруются перед сохранением. Импорт создаёт один узел
с несколькими протоколами и запись аудита `server.imported`.

Проверки: `dotnet run --project tools/VerifyServerImport` (SSH и репозиторий
изолированы; реальные протоколы на VPS не затрагиваются).

### Очистка и удаление узла

В карточке узла раздел **«Очистка и удаление узла»** доступен администратору.
Для обеих операций нужно ввести точное имя узла в диалоге подтверждения.

- **Очистить VPN на узле** — удалить зарегистрированные в панели VPN-контейнеры
  вместе с конфигурациями. Все их подключения, в том числе созданные вне панели,
  перестанут работать. Ключи панели помечаются отозванными, их секреты удаляются,
  история выдачи сохраняется. Карточка, адрес и SSH-доступ остаются; после очистки
  статус — «без протоколов», можно установить VPN заново.
- **Удалить узел из панели** — удалить карточку, сохранённый SSH-доступ
  и все документы выданных этим сервером ключей из базы, включая отозванные
  и старые ключи без привязки к протоколу. История выдачи и конфигурации этих
  ключей удаляются; журнал операций сохраняется. Ключи других узлов не затрагиваются.
  Подключение к серверу не требуется, на нём ничего не меняется. Если есть
  неотозванные ключи, в диалоге нужно явно выбрать **удаление без отзыва ключей**.
  Перед удалением неотозванные ключи отключаются в панели; при сбое удаления
  они могут временно оставаться со статусом «узел удалён» (`detached`).
  Узел удаляется после удаления его ключей, поэтому при сбое можно повторить
  операцию из его карточки. Повторные попытки отзыва удалённых ключей прекращаются.
  Это не отключает VPN-доступ: ранее выданные конфигурации могут работать,
  когда сервер включится. Через API подтверждение передаётся как `forgetKeys: true`
  вместе с `confirmationName` в теле DELETE; по умолчанию оно выключено.

Операции выполняет worker в общей очереди узла, последовательно с установкой
и выдачей ключей. Ход и ошибки отображаются в карточке, идентификатор задачи
сохраняется в URL. При частичной очистке выдача новых ключей блокируется;
после устранения ошибки очистку можно запустить повторно. Ключи отзываются
в базе только после подтверждения отсутствия соответствующего контейнера.
Автоматического повторного удаления после сбоя нет.

Очистка поддерживает стандартные зарегистрированные контейнеры WireGuard,
AWG 1/2/3 и Xray, а для `xcore` — оба его контейнера (`amnezia-xcore` и `amnezia-xcore-web`) вместе с каталогом
`/opt/amnezia-xcore` (конфиг, ключи Reality, сертификаты Caddy, российские списки): каталог удаляется только после
контейнеров, иначе Caddy успел бы создать в нём сертификаты заново. Посторонние контейнеры, образы, Docker, настройки хоста
и каталоги сборки сохраняются. Контейнеры с внешними томами/каталогами данных
отклоняются до начала удаления; штатный bind `/lib/modules` допускается и
остаётся на хосте. Незарегистрированные контейнеры автоматически не удаляются.

API: `POST /api/servers/{id}/cleanup` и `DELETE /api/servers/{id}` принимают
JSON `{"confirmationName":"точное имя узла"}` и возвращают `202` с `jobId`.
Состояние читается через `GET /api/jobs/{jobId}`. Изменение адреса или набора
протоколов после постановки в очередь отменяет операцию до SSH-действий.

Проверки: `dotnet run --project tools/VerifyServerMaintenance`; параметр
`-- --mongo=mongodb://127.0.0.1:27017` добавляет проверки на отдельной временной
базе с последующим удалением только этой тестовой базы. Реальные VPN-узлы
в проверках не используются.

### Обновление протоколов и выбор в боте

В карточке существующего сервера нажмите **«Добавить / обновить протокол»**.
AmneziaWG нового семейства реализован по релизу AmneziaVPN 5.0.2.1 и отображается
как **AmneziaWG 3.1**. Он устанавливается отдельным контейнером рядом с AWG 1/2.
Пустые поля порта и подсети означают автоматический выбор; явные значения
проверяются на пересечения. Повторная установка поверх существующего контейнера запрещена.
Для новых ключей обновите приложение AmneziaVPN.

Кнопки **«Отключить выдачу» / «Включить выдачу»** управляют доступностью новых
ключей. Они не останавливают контейнер, не отзывают старые ключи и не отключают
их мониторинг. Можно отключить выдачу для всех протоколов сервера.
В боте первичная выдача и «Новый ключ» открывают выбор доступного протокола;
ранее выданные ключи доступны через «Мои ключи». У `xcore` та же кнопка называется «Отключить узел» / «Включить узел»:
выключенный узел пропадает из ссылок подписки и из топологии (выход перестаёт получать служебного пользователя
отключённого входа), но его Xray продолжает работать и синхронизироваться.

- `POST /api/servers/{id}/protocols` — установка новой версии рядом со старой;
- `PUT /api/servers/{id}/protocols/{protocolId}/availability`, тело
  `{ "enabled": false }` — выключить выдачу новых ключей;
- `PUT /api/servers/{id}/protocols/{protocolId}/xcore` (только администратор) — настройки xcore:
  `title`, `sortOrder`, `subscriptionEnabled`, `vlessEncryption`, а у входа ещё `ruDirect`, `directDomains`,
  `proxyDomains` и `subscriptionHost` (домен, по которому вход отдаёт `/sub/`; требует
  `XCore__SubscriptionUpstream` и A-записи на этот вход). Отказ валидации несёт поле `field`.
  Установка `xcore` и остальное про подписки — в разделе [«Подписки Happ»](#подписки-happ).

Состояние установки и журнал доступны в карточке сервера. При неудаче
существующие протоколы сохраняются. Если остался контейнер незавершённой установки,
повторный запуск не удаляет его автоматически: сначала требуется диагностика на узле.
Проверки: `dotnet run --project tools/VerifyProtocols`; для проверки MongoDB
добавьте `-- --mongo=mongodb://127.0.0.1:27017` (создаётся и удаляется отдельная тестовая БД).

### `POST /api/auth/register`
Регистрация нового VPN-пользователя.
```json
{ "username": "alice", "password": "securepassword" }
```
Ответ: `{ "token": "eyJ..." }`

### `POST /api/auth/login`
Аутентификация.
```json
{ "username": "alice", "password": "securepassword" }
```

### `GET /api/vpn/config`
_(требует Bearer JWT)_

Если у пользователя на этом узле уже есть активный ключ — отдаёт готовый
VPN-конфиг сразу, `200`:
```json
{
  "vpnUri": "vpn://eJy...",
  "clientIp": "10.8.1.2",
  "clientPubKey": "abc123..."
}
```

Если ключа ещё нет, выдача синхронно по HTTP не делается — она идёт по SSH
в фоновом процессе (worker) и не укладывается в один запрос. Ответ — `202`
с идентификаторами заявки:
```json
{ "eventId": "665f...", "keyId": "665f..." }
```

Порядок для клиента: опрашивать `GET /api/events/{eventId}`, пока статус
не станет терминальным (`succeeded`/`failed`/`canceled`); по `succeeded`
повторить запрос `GET /api/vpn/config` — сработает быстрый путь выше.

`vpnUri` можно вставить в AmneziaVPN (Добавить → Вставить ссылку) или сгенерировать QR-код.

### Массовые уведомления Telegram

Раздел панели «Рассылки» доступен владельцу и администратору. API не отправляет
сообщения внутри HTTP-запроса: он создаёт кампанию и устойчивую очередь
получателей в MongoDB, которую с ограничением скорости разбирает процесс бота.

- `GET /api/notifications/audience` — число активных пользователей с Telegram;
- `GET /api/notifications` — история и прогресс кампаний;
- `POST /api/notifications` — создать и сразу запустить кампанию;
- `POST /api/notifications/{id}/cancel` — остановить ещё не выполненные доставки.

Текст отправляется без parse mode и ограничен 4096 символами. По умолчанию
диспетчер отправляет не более 20 сообщений в секунду, повторяет временные
ошибки и учитывает Telegram `retry_after`.

## Подписки Happ

Подписка — это одна постоянная ссылка `https://…/sub/<токен>`, которую пользователь добавляет в приложение
[Happ](https://www.happ.su). Приложение само перечитывает её (по умолчанию раз в 12 часов) и получает актуальный
список подключений: заблокировали узел — оператор меняет состав узлов в панели, а пользователи ничего не
переустанавливают. Подписки существуют отдельно от ключей `vpn://`: они не работают в AmneziaVPN, живут
в своей коллекции `subscriptions`, а выдача `vpn://` (бот, панель, `/api/vpn/*`) от них не зависит.

### Роли узлов: «выход» и «вход»

Подписки обслуживает собственный Xray-core (протокол `xcore`, XHTTP + Reality на порту 443), который панель ставит
сама. Узел состоит из двух контейнеров: `amnezia-xcore` (Xray) и `amnezia-xcore-web` (Caddy). Caddy держит настоящий
сертификат Let's Encrypt на домен узла и сайт-заглушку: Reality отдаёт ему рукопожатия, которые не прошли проверку,
поэтому снаружи узел выглядит обычным HTTPS-сайтом.

- **Выход** («Выход (за рубежом)») — узел за границей. К нему подключаются напрямую (запасные ссылки подписки) и
  через него выходят в интернет все, кто пришёл через вход.
- **Вход** («Вход (в РФ)») — узел в России. Клиент подключается к нему, а дальше трафик идёт на выходы. Российские
  сайты и адреса вход открывает сам, со своего IP, остальное передаёт на выход. Вход без выходов закрыт: он не выпускает
  наружу ничего, а не превращается в VPN с российским IP.

Вход нужен, чтобы клиент в России подключался к российскому адресу, а не напрямую к зарубежному, и чтобы заблокированный
выход можно было заменить, не меняя ссылку пользователя. Подойдёт ли конкретный IP входа для сетей с белыми списками,
зависит от хостера и проверяется только вручную.

### Как установить выход и вход

Что нужно от узла:

- свежий VPS; для выхода лучше адрес, который ещё не блокировали;
- SSH-доступ с пользователем, у которого есть `sudo` без пароля (Docker установка ставит сама);
- свободные порты **80 и 443**: на 443 слушает Xray, на 80 — Caddy для проверки домена (ACME HTTP-01). Если порты
  заняты другим процессом или протоколом (в том числе `amnezia-xray` на том же узле), установка откажет; по той же причине
  два `xcore` на одном узле поставить нельзя;
- домен (поддомен) с **A-записью на IPv4-адрес узла**. Перед установкой панель проверяет запись и называет, какое
  значение ожидалось; одной AAAA-записи недостаточно. Домен — латиницей, кириллический вводится как `xn--…`;
- на сервере панели задан `XCORE_ACME_EMAIL` — почта для Let's Encrypt. Без неё установка отклоняется сразу.

Порядок:

1. **Выход.** «Серверы → Добавить сервер» (протокол «Xray для подписок Happ», роль «Выход», домен) либо в карточке
   уже добавленного узла — «Добавить / обновить протокол». Установка занимает несколько минут; после запуска Caddy
   панель ждёт сертификат до двух минут. Если установка оборвалась, контейнеры убираются, а каталог узла остаётся:
   в нём уже выпущенный сертификат, а у Let's Encrypt есть лимит на выпуск сертификатов для одного домена.
2. **Вход.** То же самое с ролью «Вход» на российском VPS. Роль выбирается только при установке.
3. Worker сам приведёт все узлы `xcore` в соответствие друг другу: на выходы добавится служебный пользователь входа,
   а вход получит подключения к выходам. Для нового входа отдельным шагом скачиваются российские списки (см. ниже);
   если скачать их не удалось, установка не считается проваленной: вход работает на встроенных списках образа, а причина
   видна в его карточке.
4. В карточке входа проверьте блок «Выходы, на которые вход передаёт трафик»: у каждого выхода должно быть
   «плечо открыто». Проверку делает проход здоровья узлов (по умолчанию раз в 5 минут) с хоста входа: `curl` на домен
   выхода, ожидается ответ 200. «Плечо не отвечает» приходит с причиной (домен не разрешается, соединение отклонено, ошибка
   TLS, нет ответа за 8 с). Это наблюдение для оператора, маршрутизацию оно не меняет.
5. «Подписки → Создать подписку»: выберите пользователя, срок и квоту; кнопка «Ссылка» покажет ссылку.
6. Откройте ссылку в Happ и убедитесь, что подключения появились и работают (порядок первого запуска — в `DEPLOYMENT.md`).

Если в карточке узла показано «Узел не принял последнее изменение подписчиков», то отзыв или выдача не дошли до узла:
причина указана в тексте, повтор делает worker, а немедленно — кнопка «Сохранить» в настройках узла.

### Как устроены ссылки в подписке

`GET /sub/<токен>` отдаёт ссылки `vless://` (XHTTP, Reality, отпечаток `firefox`), по одной на подключение:

- **«через РФ»**: для каждой пары «вход × выход» ссылка ведёт на вход, а выход выбирается номером маршрута, который
  клиент подставляет в третью группу UUID (`vlessRoute`). Название — имя выхода с суффиксом « · РФ»;
- **прямые**: по ссылке на каждый выход, они идут после ссылок через вход как запасные.

Порядок внутри групп — по полю «Порядок» в настройках узла, затем по имени. В подписку входят только узлы, которые
включены и отмечены «В подписке». Название подключения — поле «Название в приложении» (до 30 символов) или имя узла.
Вместе со ссылками отдаются заголовки `profile-title`, `subscription-userinfo` (использованный трафик, квота, срок),
`profile-update-interval` и `support-url` (если задан). У истёкшей или отозванной подписки ссылок нет, а в `announce` —
сообщение об отключении; неизвестный токен получает пустой 404.

Токен — учётные данные: любой, кто знает ссылку, пользуется подпиской. «Перевыпустить» меняет и токен, и UUID, поэтому
прежняя ссылка перестаёт работать и на устройствах, где её уже импортировали. Ссылку можно показать повторно, не
перевыпуская: токен хранится в базе зашифрованным.

### Раздельная маршрутизация и списки

Правила входа проверяются сверху вниз, первое совпавшее решает:

1. приватные и локальные адреса — блок;
2. «Всегда через VPN» (список оператора) — на выход;
3. «Всегда напрямую» (список оператора) — со входа в интернет;
4. «заблокировано в РФ» (`ru-blocked`) — на выход, даже если домен в российской зоне;
5. российские домены (`category-ru`, `category-gov-ru`, `ru-available-only-inside`) и адреса (`geoip:ru`) — напрямую;
6. всё остальное — на выход.

Пункты 4 и 5 действуют при включённой настройке «РФ напрямую» (по умолчанию включена); пункт 4 и список
`ru-available-only-inside` работают, только когда на входе есть российские списки.

Списки `ru-blocked` и `ru-available-only-inside` берутся из релизов
[runetfreedom/russia-v2ray-rules-dat](https://github.com/runetfreedom/russia-v2ray-rules-dat) (репозиторий меняется
настройкой `XCore__RfListsRepo`); `category-ru`, `category-gov-ru` и `geoip:ru` встроены в образ Xray. Worker раз в сутки
смотрит, не вышел ли новый релиз, а применяет его не чаще чем раз в 7 дней (`XCore__RfListsMinAgeDays`): релизы выходят
ежедневно, а каждое применение — перезапуск Xray и обрыв соединений. Файлы скачивает сам узел, сверяет контрольную сумму
`sha256` с опубликованной в релизе и проверяет `xray run -test` с будущим конфигом, и только после этого подменяет рабочие.
Скачивание занимает очередь узла (до 300 с на файл), и пока оно идёт, синхронизация подписчиков этого узла ждёт.
Кнопка «Обновить списки сейчас» (администратор) не ждёт ни суток, ни минимального возраста. Результат — строка «Списки РФ:
релиз … от …» в карточке входа, а сбой — предупреждение «Списки РФ не обновлены: …»; оно не пропадает от очередной
синхронизации подписчиков, пока списки не обновятся. `XCore__RfListsEnabled=false` выключает списки целиком. Вход,
поставленный до появления списков, их каталога не видит: обновление ему откажет, а чинится это переустановкой протокола
`xcore` на узле.

Свои списки «Всегда напрямую» и «Всегда через VPN» нужны для сервисов, которые общие списки определяют неверно. По одному
домену в строке: имя без префикса означает сам домен и его поддомены; допустимы также `full:` и `keyword:`. Регулярные
выражения, `geosite:` и `ext:` оператору закрыты. Не более 1000 записей в списке. DNS входа идёт через DoH к `1.1.1.1` и
`8.8.8.8`, а не через резолвер хостера, чтобы хостер не видел посещаемые сайты.

Российские сайты со входа видят IP входа, а не домашний адрес пользователя. Если сервису нужен домашний IP, остаётся
профиль маршрутизации Happ (ниже): тогда российские сайты идут напрямую с устройства. Через вход при этом идёт весь
остальной российский трафик пользователей, поэтому канал и нагрузку входа выбирайте с запасом.

### Настройки узла и домен подписки

В карточке узла «Настройки подписки» (администратор): название в приложении, порядок, «В подписке», шифрование VLESS и,
у входа, «РФ напрямую», списки «Всегда напрямую» и «Всегда через VPN» и **«Домен подписки на этом входе»**. После
сохранения узлы синхронизируются в фоне: вход и выходы зависят друг от друга, поэтому обновляются все.

Домен подписки входа нужен, чтобы ссылка подписки открывалась из России и в зонах белых списков, где сервер панели
за границей может быть недоступен: Caddy входа сам проксирует `/sub/` на API панели. Требования: A-запись домена на IP
этого входа (панель проверяет её при сохранении), домен отличается от домена узла, а на сервере панели задан
`XCORE_SUBSCRIPTION_UPSTREAM` — публичный адрес API панели. Если домен подписки задан хотя бы у одного входа, ссылки
строятся на него, а `SUBSCRIPTION_PUBLIC_BASE_URL` остаётся запасным адресом (`fallback-url`, если включён Provider ID).
Подробности и второй вариант (подписка на сервере панели) — в `DEPLOYMENT.md`.

Если сертификат для домена подписки получить не удалось, Caddy в течение 60 минут (`XCORE_CADDY_RETRY_MINUTES`) с тем же
Caddyfile не перезапускается: Let's Encrypt после серии неудач блокирует выпуск. В карточке будет «повтор не раньше HH:mm UTC»;
паузу снимает исправленный домен или кнопка «Сохранить» в настройках узла.

### Опции, выключенные по умолчанию

Эти возможности включает оператор, и у каждой есть цена.

- **Профиль маршрутизации Happ** (`SUBSCRIPTION_HAPP_ROUTING_ENABLED=true`, название — `SUBSCRIPTION_HAPP_ROUTING_NAME`,
  по умолчанию «RU direct»). Подписка отдаёт заголовок `routing`: российские сайты и адреса идут напрямую с устройства
  пользователя, минуя вход, а `ru-blocked` — через туннель. Вход освобождается от российского трафика этих пользователей,
  но российские сайты видят их домашний IP. Файлы списков Happ скачивает сам с `runetfreedom/russia-v2ray-rules-dat`
  (адрес зашит в профиле и не следует за `XCore__RfListsRepo`). Заголовок получает только действующая подписка.
- **Provider ID** (`SUBSCRIPTION_HAPP_PROVIDER_ID`). Подписка отдаёт заголовок `providerid`, а когда основная ссылка
  построена на домене подписки входа, ещё и `fallback-url`: ту же ссылку на адресе панели, на которую приложение
  переключится, если основная недоступна. **Предупреждение:** с Provider ID Happ раз в день отправляет на
  `check.happ-proxy.com` идентификатор устройства (HWID), хеш домена подписки и версию ОС, то есть третья сторона узнаёт
  о числе и составе устройств подписки. Значение с пробелом, управляющим символом или не-ASCII считается невалидным
  и игнорируется.
- **VLESS Encryption** (`mlkem768x25519plus`, переключатель в настройках узла). Ключи создаются на узле при включении,
  серверная часть хранится в базе зашифрованной, а ссылки подписки и подключения входов к этому выходу получают клиентскую
  часть. **Предупреждение:** поддержка в Happ документацией не подтверждена, а клиент без неё не подключится к узлу
  вовсе. Включайте только после проверки в Happ на одном устройстве. Узел перезапускается, у выхода перерисовываются
  конфиги входов, а на устройствах со старой копией подписки узел не будет работать до её обновления. Выключение стирает ключи.

### Бот: «📲 Подписка Happ»

В главном меню бота появляется кнопка «📲 Подписка Happ», если в панели есть хотя бы один выход в подписках. Она выдаёт
ссылку (с кнопкой «📋 Скопировать ссылку», если ссылка не длиннее 256 символов), срок и трафик, короткую инструкцию
(установить Happ, скопировать ссылку, в Happ «+» → «Вставить из буфера») и отдельным сообщением QR-код ссылки для
сканирования с другого устройства — только для действующей подписки. Если не настроены ни `SUBSCRIPTION_PUBLIC_BASE_URL`
(его читает и бот), ни домен подписки у входа, бот отвечает «Подписки временно недоступны».

Правило повторной выдачи: если у пользователя нет активной подписки, а прежняя закончилась **по сроку**, бот выдаёт новую
автоматически (срок и квота по умолчанию из настроек панели). Если прежнюю отозвали **по исчерпанию квоты** или **вручную**,
новую бот не выдаёт и отвечает «Подписка отключена (…). Обратитесь к администратору»: иначе кнопка обходила бы решение
администратора и квоту. Из панели администратор выдаёт подписку всегда. Активная подписка у пользователя только одна.

### Учёт трафика, сроки и квоты

Worker снимает счётчики Xray по каждому подписчику с каждого узла (по умолчанию раз в 60 с) и накапливает приращения.
Счётчики обнуляются при перезапуске контейнера, и приращение, набежавшее между последним опросом и перезапуском, теряется.
Трафик считается там, куда подключается клиент: на входе для ссылок «через РФ» (включая российские сайты, которые вход
открывает сам) и на выходе для прямых ссылок; служебный трафик входа к выходам в подписки не попадает. Раз в минуту сроки
и квоты проверяет `EnforcementService`: просроченная или исчерпавшая квоту подписка отзывается. Ссылка перестаёт отдавать
узлы сразу, а подключение на уже настроенных устройствах прекращается, когда узлы применят синхронизацию. Раз в 15 минут
(`Polling__XCoreReconcileIntervalMinutes`) worker страховочно переиздаёт синхронизацию, если событие потерялось или узел
разошёлся с базой.

### API

- `GET /api/subscriptions` — список с фильтрами `search`, `status`, `userId`, `page`, `pageSize`; `GET /api/subscriptions/{id}` —
  карточка (owner, admin, operator, viewer);
- `POST /api/subscriptions` — выдать подписку, тело `{ "userId": "…", "expiryDays": 30, "trafficLimitBytes": 107374182400 }`
  (не передано — по умолчанию из настроек панели, `0` — без ограничения);
- `GET /api/subscriptions/{id}/link` — публичная ссылка (ответ не кэшируется); `POST /api/subscriptions/{id}/revoke`;
  `POST /api/subscriptions/{id}/regenerate`; `PUT /api/subscriptions/{id}/limits` с телом
  `{ "expiresAt": "…", "trafficLimitBytes": … }` (owner, admin, operator);
- `GET /sub/{token}` — ссылка подписки, без авторизации: не более 30 запросов в минуту на токен и 600 в минуту на весь
  маршрут, `Cache-Control: no-store`;
- `PUT /api/servers/{id}/protocols/{protocolId}/xcore` (администратор) — настройки узла: `title`, `sortOrder`,
  `subscriptionEnabled`, `vlessEncryption`, а у входа ещё `ruDirect`, `directDomains`, `proxyDomains` и `subscriptionHost`;
- `POST /api/servers/{id}/protocols/{protocolId}/xcore/rf-lists/update` (администратор) — обновить российские списки входа,
  ответ `202`.

Токен и UUID подписки не попадают в ответы API панели (кроме ссылки в `GET /api/subscriptions/{id}/link`), в журнал и в логи.

## Формат `vpn://`

Совместим с [exportController.cpp](../amnezia-client-dev/client/ui/controllers/exportController.cpp):
1. JSON → UTF-8 bytes
2. qCompress: 4 байта big-endian (размер оригинала) + zlib RFC 1950
3. Base64 URL-safe без padding
4. Префикс `vpn://`

## MongoDB-схема

База `amnezia_vpn`; схему правят только миграции worker (`_migrations`), и применяются они при его старте.
Схема эволюционирует на месте: те же коллекции и `_id`, потому что на `clients.serverId` ссылается каждый выданный ключ.

| Коллекция | Содержимое |
|---|---|
| `server_config` | узлы: имя, адрес, зашифрованный SSH-доступ, статус и список `protocols[]`. У каждого протокола — `kind`, `containerName`, `port`, `state`, `enabled` и группа параметров: `wg` (семейство WireGuard), `xray` или `xcore` |
| `clients` | выданные ключи `vpn://`: владелец, узел и протокол, адрес и ключи peer-а, статус, срок, квота, счётчики трафика |
| `users`, `passcodes`, `refresh_sessions` | пользователи и роли, пригласительные коды, refresh-сессии панели (хранятся хеши) |
| `subscriptions` | подписки Happ: владелец, статус, срок, квота, хеш токена и токен в зашифрованном виде, UUID, накопленный трафик и сырые показания счётчиков по узлам |
| `subscription_usage_daily`, `key_usage_daily`, `server_usage_daily`, `server_health_daily` | суточные срезы трафика и здоровья (хранятся 400 дней) |
| `install_jobs`, `install_job_logs` | задачи установки, очистки и удаления узлов и их журнал |
| `domain_events`, `leases` | шина доменных событий и аренды (партиция узла, таймерные воркеры) |
| `audit_log`, `panel_settings` | журнал операций и настройки панели (срок и квота по умолчанию) |
| `notification_campaigns`, `notification_deliveries` | рассылки Telegram и очередь доставки |
| `router_monitors`, `router_history` | наблюдение за роутерами |

Параметры `xcore` в узле: роль, домен, закреплённый образ, ключи Reality (приватный — зашифрованный), номер маршрута
выхода (`routeId`), служебный UUID входа (зашифрованный), настройки маршрутизации входа, домен подписки, тег релиза
российских списков и ревизии применённых конфигов. Уникальность `protocols.xcore.routeId` держит sparse-индекс (миграция 017),
а «одна активная подписка на пользователя» — частичный уникальный индекс по `subscriptions.userId` (миграция 016).
