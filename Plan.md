## Контекст

Был сервис с Telegram-ботом: пользователь вводит инвайт-код, выбирает сервер,
получает `vpn://`-ключ. Управление — только через Swagger.

Задача: сделать админ-панель по макету
`D:\Amnezia\AmneziaVPN админ-панель\Панель AmneziaVPN.dc.html`. Макет описывает
существенно больше, чем умел бэкенд: три протокола вместо одного, авто-установка
Docker и контейнеров по SSH, трафик, сроки действия ключей, журнал событий.
Выбран вариант **полной реализации дизайна**.

Оригинальные скрипты установки Amnezia лежат локально в
`D:\Amnezia\amnezia-client-dev\client\server_scripts\` — переиспользуются
дословно.

### Решения, принятые на старте

| Вопрос | Решение |
|---|---|
| Объём | полная реализация дизайна |
| Авторизация | роль в `User` + JWT-claim + сидирование владельца из конфига |
| Фронтенд | отдельный Vite-проект в репозитории, в проде за nginx |
| Стилизация | `styles.css` дизайн-системы как есть + CSS-модули поверх |

## Фаза 0 — Хардненинг и фундамент ✔

Роли (`owner`/`admin`/`operator`/`viewer`/`client`), claim роли в JWT, политики
`PanelRead`/`PanelWrite`/`PanelAdmin`/`PanelOwner`. Сидирование владельца при
каждом старте. `/api/auth/register` закрыт инвайт-кодом и жёстко ставит роль
`client`. Rate limit на логине. Валидация JWT-секрета. Глобальный
`ProblemDetails`. Устранена утечка SSH-команд в тела ответов. `ISecretProtector`
на AES-GCM. Миграции 001–002.

**Проверено:** бот и `/api/vpn/*` работают идентично; клиентский JWT получает 403
на маршрутах панели; SSH-ошибка отдаёт обобщённый 502; старт с плейсхолдерным
секретом невозможен; rate limit срабатывает.

**Найдено по ходу.** `User.TelegramId` писался явным `null`, а уникальный
sparse-индекс исключает только *отсутствующее* поле. Любые два пользователя без
Telegram падали с `E11000`. Не проявлялось, потому что HTTP-пользователь был
один. Починено `[BsonIgnoreIfNull]` + миграция 002.

**Отступления от плана.** Сидирование владельца сделано `IHostedService`, а не
миграцией: миграция отрабатывает однократно, а проверка нужна при каждом старте.
Аутентификация MongoDB отложена в фазу 6 — `MONGO_INITDB_ROOT_*` не срабатывает
на заполненном томе, и автодеплой оторвал бы API от базы.

## Фаза 1 — Модель данных v2 + read-only API ✔

`VpnServer` со списком `ProtocolInstance` (`wg`/`xray` как nullable-группы,
без BSON-дискриминаторов). `VpnClient` v2: протокол, `shortId`, статус, срок,
квота, счётчики трафика. Новые коллекции: `audit_log`, `panel_settings`.
Репозитории с поиском и пагинацией. Миграции 003–007. Read-only API панели.
`PUT /api/servers/{id}` переведён на patch-семантику.

**Проверено:** мигрированный узел отдаётся с одним awg-протоколом, порт 42174
и пути сохранены дословно; секреты наружу не уходят; поиск экранирует
спецсимволы regex; ключи, пользователи, журнал и настройки читаются.

**Найдено по ходу.** Драйвер MongoDB мапит любое свойство `Id` в `_id`,
игнорируя `[BsonElement("id")]`. У вложенного `ProtocolInstance` это означало
новый Guid при каждом чтении — любое сохранение узла осиротило бы `protocolId`
всех ключей. Починено `[BsonNoId]` + миграция 007, восстанавливающая исходный
идентификатор.

**Отступления.** Уникальный индекс по назначенным IP вынесен в миграцию 006:
MongoDB не принимает `$ne` в `partialFilterExpression`, заменено на `$in`.
Прежний PUT перезаписывал незаполненные поля значениями по умолчанию — запрос
без `awgPort` молча менял реальный порт узла на 55424.

## Фаза 3 — Абстракция протоколов, выдача и отзыв ✔

`ISshSession` — единственная точка работы с узлами. `IProtocolConfigurator`:
один конфигуратор на семейство WireGuard (три варианта различаются четырьмя
значениями профиля) плюс отдельный для Xray. Аллокатор IP переписан на
«наименьший свободный». `POST /api/keys`, отзыв, скачивание. Экран выдачи,
диалог отзыва, тосты. Legacy-слой (`AwgServerConfig`, `AwgServerService`,
адаптер) удалён полностью.

**Проверено:** путь ошибок (502 без утечки команд), валидация, разделение ролей,
запись неудачи в журнал с уровнем «ошибка», отсутствие мусорных записей.

**Главное — формат `vpn://` впервые проверен.** Коллекция `clients` была пуста,
то есть ни один ключ сервиса никогда не импортировался в живой AmneziaVPN.
`tools/VerifyVpnUri` сверяет результат поле за полем с ожиданиями
`exportController.cpp`: структура `last_config`, `port` числом, `clientId`,
обфускация в обоих регистрах, `protocol_version` только у awg2, отсутствие
S3/S4 у legacy, заголовок qCompress, base64url без padding, неэкранированный
`I1`, полный набор полей Reality.

**Найдено по ходу.** Владелец ключа создавался *до* проверки сервера
и протокола — каждый неудачный запрос оставлял мусорную учётку. Slug из
русского имени вырождался в `client`, `client-2`, `client-3`.

**Отступления.** Отзыв при недоступном узле переводит ключ в `pendingRevoke`,
а не в `revoked`: пока peer жив на сервере, доступ у клиента остаётся.

## Фаза 4 — Оркестрация установки и мастер ✔

`InstallJob` + отдельная коллекция логов + фоновый воркер (канал,
`SemaphoreSlim(2)`, один активный job на узел). Шесть шагов 1:1 с чеклистом
макета, взвешенный прогресс, отмена на границах шагов. `IProtocolInstaller`
поверх скриптов upstream (29 файлов как embedded-ресурсы). `POST /servers/install`
с ответом 202, `test-connection`, API задач. Четырёхшаговый мастер с опросом
задачи и хвостом лога, состояние адресуемо через `?job=`.

**Проверено:** валидация до создания чего-либо (пустые протоколы, отсутствие
кредов, дубли подсетей), 202 с `jobId`, задача падает на шаге `ssh` с понятным
сообщением, остальные шаги остаются `pending`, узел переходит в `error`, лог без
секретов, вторая установка на тот же узел отклоняется, `test-connection`
сообщает о проблеме вместо исключения, разделение ролей.

**Решения.** `set -e` в скрипты не добавлен намеренно. Порт по умолчанию
случайный из 30000–50000, параметры обфускации генерируются на каждый узел —
постоянные значения сами становятся сигнатурой. Разные подсети для wg-протоколов
проверяются явно: два контейнера в одной подсети конфликтуют по NAT. Удаление
протокола блокируется при наличии активных ключей.

**Исправлено позже: скрипты установки не попадали в сборку.** Маски
`EmbeddedResource` в `AmneziaKeyService.Infrastructure.csproj` покрывали только
`*.conf` и `*.json` — клиентские шаблоны из фазы 3. Скрипты установки и четыре
`Dockerfile`, появившиеся в фазе 4, в сборку не включались: в манифесте
собранной сборки лежало 4 ресурса вместо 28. Любая установка упала бы на первом
же `ScriptRegistry.Read` — то есть фаза 4 не работала вообще.

Почему не заметили: до чтения скриптов дело доходит только после успешного
SSH-подключения, а единственный доступный узел был мёртв. Задача честно падала
на шаге `ssh`, и это приняли за проверку пути ошибок.

Маска заменена на каталог целиком (`ServerScripts\**\*` минус `*.md`) —
перечисление расширений обязано разойтись с содержимым каталога рано или поздно.
В `tools/VerifyMonitoring` добавлен барьер: чтение всех 24 скриптов и 4 шаблонов
через `ScriptRegistry`. Барьер проверен в обе стороны — со старыми масками
падает, с новой проходит.

## Фаза 5 — Статистика, здоровье, сроки и квоты ✔

Четыре фоновых воркера поверх общей базы `PeriodicWorker` (scope на узел,
ограничение параллелизма, сбой тика не останавливает цикл): `StatsPollerService`
(60 с), `HealthPollerService` (300 с), `EnforcementService` (60 с),
`ReconcileService` (24 ч). Интервалы и общий выключатель — секция `Polling`;
локально воркеры выключены по умолчанию.

Разбор `docker exec <c> <bin> show <iface> dump` вынесен в `WgDumpParser`:
строки отбираются по числу полей, а не «пропустить первую» — при лишнем выводе
разбор не съедет на peer-ов. Строка интерфейса содержит приватный ключ сервера
и в модель `WgPeer` не попадает вовсе. Суточные срезы `key_usage_daily`,
`server_usage_daily`, `server_health_daily` с детерминированным `_id`
`{владелец}:{дата}` и TTL 400 дней; обновление — upsert с `$inc`, поэтому
повтор тика после сбоя не задваивает данные и не требует транзакции.
Миграция 009.

Захардкоженные нули убраны: трафик узла и парка, аптайм за 30 дней. Отзыв
по сроку и квоте переиспользует `RevokeAsync` — она уже умеет `pendingRevoke`
при недоступном узле, ретрай делает тот же тик.

**Проверено.** Офлайн — 27 проверок в `tools/VerifyMonitoring`: разбор dump
поле за полем, `(none)` и нулевой хэндшейк, мусорная строка, арифметика сброса
счётчиков таблицей случаев, редактирование секретов. Вживую на локальной базе:
миграция 009 создала все индексы, включая TTL по `expireAt`; при недоступном
узле health-воркер записал срез `checksTotal=1, checksOk=0` с `expireAt` ровно
на 400 дней вперёд, перевёл узел в `offline` с записью в журнал; reconcile
корректно **не** записал «расхождений нет» — `reconciledAt` остался null,
потому что прочитать peer-ов не удалось. `$expr`-фильтр квоты отработал
на живом драйвере. Регрессия формата `vpn://` — 67 проверок без провалов.

**Решения.**

`Expired` как статус не используется: истёкший ключ получает `revoked`
с `revokeReason = "expired"`. Причина в миграции 006 — `Expired` входит
в список статусов, удерживающих туннельный IP, а peer уже удалён с узла,
и адрес обязан освободиться. Статус остаётся зарезервированным под мягкое
истечение, когда peer на узле оставляют.

Аптайм — отношение сумм проверок, а не среднее по дням: сутки с одной проверкой
не должны весить столько же, сколько полные.

Дата в срезах — строка ISO, а не `DateTime`: лексикографический порядок
совпадает с хронологическим, диапазонные запросы работают как есть, документ
читается глазами в `mongosh`.

Аптайм узла берётся из `/proc/uptime`, а не из `uptime -s`: второй печатает
время в часовом поясе узла, и на сервере не в UTC момент загрузки уезжал бы
на часы. Числа разбираются в инвариантной культуре с заменой запятой на точку:
`awk` на узле с русской локалью печатает «12,5».

Сверка ничего не удаляет — только считает и сообщает.

**Найдено по ходу.** Квота приходила в `IssueAsync` как есть, и ноль означал бы
«ноль байт», то есть исчерпание первым же пакетом: ключ с лимитом 0 отзывался бы
через минуту после выдачи. Приведено к семантике срока — 0 значит «без
ограничения», null — «взять из настроек панели».

**Заведомо недоступно.** Пер-юзерная статистика Xray: в генерируемом upstream
`server.json` нет блока `stats`/`api`. Отдаём `null`, в UI прочерк с подсказкой
о причине — ноль читался бы как «не пользуются».

## Логи в Seq ✔

Логирования как инфраструктуры в проекте не было вовсе: дефолтный консольный
вывод и секция `Logging.LogLevel`. Пока всё происходило по HTTP-запросу,
`docker logs` хватало; с четырьмя круглосуточными воркерами — нет.

Serilog со стоком в Seq, консоль остаётся всегда. Скоупы с `ServerId`,
`ServerName`, `KeyId`, `Worker` открываются на итерацию воркера, а не
подставляются в каждое сообщение, — в Seq история узла или ключа собирается
запросом. Infrastructure о Serilog не знает: свойства идут через
`ILogger.BeginScope`.

**Секреты сделаны свойством транспорта.** `SecretRedactor` вызывался точечно
по месту — на выводе SSH и на строках лога установки. Для внешнего хранилища
этого мало: одной новой строки `LogDebug` с сырым выводом `wg show dump`
хватило бы, чтобы приватный ключ сервера осел в базе Seq и пережил там
и удаление узла, и пересоздание контейнера. `SecretRedactingSink` оборачивает
оба стока и чистит два канала: строковые свойства события и текст шаблона
(последнее ловит интерполяцию `$"...{secret}"`, которая свойств не создаёт
вовсе). Плейсхолдеры при срабатывании перестают подставляться — остаться
с невнятным сообщением лучше, чем с ключом в базе логов.

Тик без изменений логируется на `Debug` и по умолчанию выключен: опрос раз
в минуту по каждому узлу иначе дал бы десятки тысяч событий в сутки.

`audit_log` не тронут: журнал в Mongo — то, что видит владелец панели, с ролевым
доступом; Seq — оперативная диагностика. Сшиваются по `KeyId` и `JobId`.

Интерфейс Seq привязан к `127.0.0.1:8082`: 8080 и 8081 заняты API и панелью,
а выставлять наружу беспарольный интерфейс у сервиса, который ворочает
VPN-ключами, нельзя. Порт приёма 5341 не публикуется вовсе. Пустой
`Seq__ServerUrl` отключает сток — локальный `dotnet run` работает без Seq.

**Найдено по ходу.** Проверка редактирования сначала провалилась — и виноват
оказался не редактор, а тестовый ключ длиной 42 символа вместо 43.
`Base64Key()` опознаёт секрет по точной длине base64 32-байтного ключа,
и укоротить ключ значит пройти сквозь фильтр. Настоящие ключи X25519 всегда
44 символа с `=`, так что на практике это не дыра, но в фикстуре зафиксировано
комментарием.

## Разделение на процессы — шаг A ✔

Первый шаг перехода на доменные события: три процесса вместо одного, семантика
не менялась.

`api` — только HTTP. `worker` — миграции, сидирование владельца и четыре воркера
эксплуатации. `bot` — Telegram. Композиция вынесена в
`Infrastructure/DependencyInjection/`: `AddAmneziaData`, `AddAmneziaProtocols`,
`AddAmneziaNodeAccess`. Последнее — граница доступа к узлам, выраженная кодом:
кто его не вызвал, тот не откроет SSH, потому что в его контейнере нет
`ISshSessionFactory`. Бутстрап логирования переехал туда же — обёртка
редактирования секретов обязана стоять во всех трёх процессах, а три копии
в трёх `Program.cs` разошлись бы молча.

Один `Dockerfile` на все три образа, проект выбирается аргументом сборки.
Токен бота теперь только в контейнере бота, `ADMIN__PASSWORD` — только
в воркере.

**Проверено вживую.** Все три образа собираются; воркер поднимает четыре
воркера эксплуатации и применяет миграции; api отвечает 401 на защищённом
маршруте. Ворота схемы проверены в обе стороны: на готовой базе пропускают
молча, на пустой — держат HTTP и раз в три секунды пишут, каких миграций ждут.

**Найдено по ходу.** `MongoSchemaGate` падал на старте: драйвер MongoDB
не переводит `Project(d => d["_id"].AsString)` для `BsonDocument`
в LINQ-выражение. Поймал смоук-прогон контейнера — сборка на это не жалуется.

**Отступления от плана.** Воркер установки остался в api. Очередь — канал
в памяти, а он не переживает границу процессов; заменять его сейчас опросом
значило бы писать код, который следующий шаг удалит. Вместе с ним в api
пока остаются SSH и ключ шифрования — они уйдут, когда установка и выдача
ключа переедут на события.

**Следующее.** Шина доменных событий, затем установка на неё, затем ключи.
План целиком — `C:\Users\Admin\.claude\plans\tender-questing-hennessy.md`.

## Разделение на процессы — шаг B ✔

Шина доменных событий поверх MongoDB. Обработчиков пока нет — их приносят
следующие шаги, — но механизм готов и проверен.

`domain_events` с атомарным захватом через `findOneAndUpdate`: он атомарен
на уровне документа и на standalone, где нет ни транзакций, ни change streams.
Аренда с пульсом вместо флага «в работе»: процесс может исчезнуть, не сняв
флаг, и событие зависло бы навсегда. Коллекция `leases` — сериализация
операций по узлу и, позже, выбор единственного активного таймерного воркера.
Взятие аренды — upsert с условием, где дубликат ключа означает «занято».
Миграция 010.

**Политику повторов объявляет обработчик**, а не общая таблица: идемпотентность
— свойство операции, и знает о ней только тот, кто её выполняет. Жнец
просроченных аренд разбирает события по этой политике и только тех типов,
которые процесс сам умеет обрабатывать: о чужой идемпотентности он ничего
не знает.

**Проверено на живой базе** — `tools/VerifyEvents`, 36 проверок на временной
базе с уборкой за собой. Кроме примитивов проверены две вещи, которые
последовательным тестом не показать: восемь потребителей разбирают шестьдесят
событий, и ни одно не достаётся двоим; два настоящих диспетчера обрабатывают
очередь параллельно, но операции над одним узлом не пересекаются во времени.
Рядом стоит проверка, что разные узлы при этом **пересекались** — без неё
первая проходила бы и на строго последовательной обработке, то есть не
доказывала бы ничего. Прогон трижды подряд даёт одинаковый результат.

**Найдено по ходу.** Первая версия проверки сериализации падала — и виноват
оказался не диспетчер, а сама проверка: `ReferenceEquals` на кортежах-значениях
всегда false, поэтому каждый отрезок сравнивался сам с собой, а сам с собой
он пересекается всегда.

**Отступление от плана.** `PeriodicWorker` был завязан на `PollingOptions`,
то есть `Polling:Enabled=false` на машине разработчика погасил бы и шину
событий — панель молча перестала бы выдавать ключи. Расписание развязано
в `WorkerSchedule`, у шины свой выключатель `EventBus:Enabled`.

**Не сделано.** `tools/VerifyEvents` не добавлен в CI: ему нужен сервисный
контейнер MongoDB, а проверить такой шаг локально не удалось — Docker Desktop
на машине разработчика перестал отвечать посреди проверки. Добавлять
непроверенный шаг в развёртывание не стал.

## Разделение на процессы — шаг C ✔

Установка переехала на события. `InstallService` создаёт задачу и публикует
`server.install` с ключом партиции по узлу; `InstallJobQueue` и `InstallJobWorker`
удалены. Работу делает `InstallEventHandler` в worker, вызывая тот же
`InstallOrchestrator`. Панель не изменилась — она по-прежнему читает
`/api/jobs/{id}`.

**Событие и задача разделены по смыслу.** Оркестратор разбирается со своими
ошибками сам, поэтому неудачная установка — это успешно доставленное
и исполненное событие с неуспешной задачей. Событие отвечает за доставку,
задача — за то, что видит оператор.

**Найдено при проектировании: задача зависала бы навсегда.** Раньше
`InstallJobWorker` при старте помечал прерванными задачи в статусе running.
После переезда этого не стало, а жнец знает только про события — задача
осталась бы «выполняется» вечно, показывая оператору вечный прогресс.
Появился `IDomainEventHandler.OnFailedAsync`: диспетчер и жнец зовут его
при окончательном провале, и обработчик прибирает за собой. Пометка при старте
не вернулась намеренно — она была бы неверна при нескольких экземплярах worker,
убивая задачу, которую подхватил соседний процесс.

**Проверено вживую, двумя контейнерами на пробной базе.**

Установка на несуществующий узел: задача провалилась на шаге `ssh`, остальные
шаги остались `pending`. В логе worker — исполнение и «Событие server.install
выполнено»; в логе api про установку **нет ничего**. Это и есть проверяемое
свойство: работа ушла из веб-процесса.

Смерть исполнителя посреди работы: worker убит через пять секунд после начала,
задача осталась `running` — то самое состояние, ради которого написан жнец.
После подъёма worker событие ушло в `failed` с формулировкой «операция
не допускает повтора» (политика Once, установка заново **не** запускалась),
а задача получила статус `failed` и внятное сообщение оператору.

**Отступление.** Границы DI уточнены: инсталляторы SSH не требуют и переехали
в `AddAmneziaProtocols` — api нужен их реестр, чтобы отклонить неподдерживаемый
протокол до создания задачи. Исполнение вынесено в `AddAmneziaInstallExecution`,
который вызывает только worker, поэтому оркестратора у api теперь нет физически.

**Осталось в api.** SSH никуда не делся: выдача ключа синхронна до шага D,
а `POST /servers/test-connection` — синхронная диагностика второго шага мастера,
и её перенос планом не предусмотрен. Это открытый вопрос, а не забытый хвост.

## Открытые вопросы

**Ручной browser smoke панели не выполнен.** Статические проверки TypeScript,
линтера, production-сборки и accessibility-паттернов пройдены, но интерактивная
проверка всех маршрутов, фокус-ловушки и мутаций требует работающего API и
изолированных тестовых данных.

**Сквозной тест не выполнен.** Выдать ключ → импортировать в AmneziaVPN →
подключиться → отозвать, и полный прогон мастера установки на чистом VPS.
Требует живого узла.

Про установку это особенно важно: пока её ни разу не доводили дальше шага `ssh`,
в сборку не попадали сами скрипты (см. фазу 4). Дефект устранён и закрыт
проверкой, но это означает, что шаги `docker`, `containers`, `keys_and_fw`
и `verify` не выполнялись на живой машине **ни разу**. Первый прогон на чистой
Ubuntu 22.04 или Debian 12 стоит считать не подтверждением, а собственно
испытанием — и закладывать время на разбор.

**Боевой узел `89.44.85.223` недоступен.** На VNC-консоли:

```
EXT4-fs error (device vda1): bad block bitmap checksum
Aborting journal on device vda1-8
EXT4-fs (vda1): Remounting filesystem read-only
```

Корневая ФС в режиме только для чтения — отсюда обрыв SSH на обмене версиями
и, вероятно, более раннее `Permission denied (password)` (PAM не смог писать
в `/var/run/faillock/`). Пароль менять не нужно. Порядок: вытащить через VNC
`wireguard_server_private_key.key` и `wg0.conf` (там все выданные peer-ы), затем
`e2fsck -f -y /dev/vda1` из режима восстановления, затем обращение к провайдеру —
`bad block bitmap checksum` часто указывает на сбой хранилища.

В базе есть `serverPubKey`, PSK и параметры обфускации, но **нет приватного
ключа сервера**, а коллекция `clients` пуста: все 13 peer-ов заведены мимо
сервиса. Если диск не восстановится, всем клиентам понадобятся новые конфиги.

**Проверки не входят в solution и запускаются отдельно.** Офлайн-набор состоит
из `tools/VerifyVpnUri` (формат `vpn://`), `tools/VerifyMonitoring` (разбор
`wg dump`, арифметика счётчиков и редактирование секретов),
`tools/VerifyUserManagement`, `tools/VerifyPanelSettings` и
`tools/VerifyRefreshTokens`. `tools/VerifyEvents` и
`tools/VerifyLegacyMigration` требуют MongoDB, создают отдельную временную БД
и удаляют её после завершения. `tools/VerifyMongoAuthentication.ps1` создаёт
одноразовые container/volume и очищает их в `finally`; для существующего тома
`tools/VerifyMongoApplicationUri.ps1` только проверяет подготовленную
credentialed URI перед включением `--auth`. Фронтенд проверяется отдельно
`npm run typecheck`, `npm run lint`, `npm run verify:a11y` и `npm run build`.
Эти команды являются ручной верификацией; включение их в CI этим документом
не утверждается.

**Telegram-токен больше не хранится в versionable-конфигурации.** Он задаётся
только через `TelegramBot__Token`, `.env` или secret manager; перед первым
коммитом всё равно проверяйте staged diff на случайный локальный секрет.

**Репозиторий не инициализирован** — `.git` отсутствует. `.gitignore` добавлен.

**Пер-ключевой трафик ни разу не проверен на живом узле.** Приёмка фазы 5
требует: трафик появляется в пределах одного интервала опроса и продолжает
накапливаться через `docker restart` контейнера; ключ с прошедшим `expiresAt`
отзывается за минуту; «Трафик за месяц» равен сумме суточных срезов. Всё это
упирается в тот же недоступный узел.

**Отзыв открывает SSH-сессию на каждый ключ.** Для редких событий это норма,
но массовое истечение (пачка ключей одного узла в один день) даст пачку
подключений подряд. Если станет заметно — группировать кандидатов по узлу
и отзывать в одной сессии.

## Риски

1. **Надёжность установки между дистрибутивами.** Upstream предполагает
   беспарольный sudo, знакомый пакетный менеджер, ядро ≥4.14 для awg2;
   `docker build --no-cache --pull` занимает 3–8 минут и может словить OOM.
   Нужен ручной прогон на Ubuntu 22.04 и Debian 12.
2. **Управление клиентами Xray перезапускает контейнер** — каждая выдача
   и отзыв роняют активные соединения на пару секунд.
3. **Учёт трафика через рестарты** — приращение, накопленное между последним
   опросом и рестартом контейнера, теряется безвозвратно: узнать его неоткуда.
   Принято осознанно, а не решается.
4. **Секреты в Mongo.** Шифрование защищает от дампа базы, но не от
   компрометации хоста: ключ лежит в том же `.env` на той же машине.
5. **Seq как новое место хранения секретов.** Обёртка стока вырезает то, что
   умеет узнавать `SecretRedactor`: PEM-блоки, присваивания вида
   `PrivateKey = …`, base64-ключи ровно нужной длины, именованные переменные
   скриптов. Секрет другого формата она пропустит. Том Seq заслуживает того же
   отношения, что и дамп базы.
